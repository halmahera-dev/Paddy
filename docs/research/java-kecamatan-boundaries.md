# Java kecamatan boundaries and IDs

Checked: 27 September 2026. This is a source and small API check, not a full Java import or a legal review of reuse rights.

## Finding

Use BIG's **June 2026 `BATAS_KECAMATAN_AR_2026`** as the candidate boundary snapshot for Java-wide screening. BIG is the publisher. The national data portal dates its publication and modification to **21 August 2026**. BIG says each *kecamatan* polygon is an aggregate of June 2026 village polygons with the same `KDCPUM` code. The [dataset entry](https://data.go.id/dataset/dataset/batas_kecamatan_ar_2026) links to BIG's [polygon MapServer](https://geoservices.big.go.id/rbi/rest/services/BATASWILAYAH/BATAS_KECAMATAN_AR/MapServer). The service supports JSON and GeoJSON queries in EPSG:4326, with a 1,000-feature response limit; an operator can request IDs and then fetch features in batches. [BIG service metadata](https://geoservices.big.go.id/rbi/rest/services/BATASWILAYAH/BATAS_KECAMATAN_AR/MapServer?f=pjson) · [BIG layer metadata](https://geoservices.big.go.id/rbi/rest/services/BATASWILAYAH/BATAS_KECAMATAN_AR/MapServer/0?f=pjson)

**Publication gate:** The portal marks the dataset **“Terbuka”** and tags it “Downloadable Data,” but its listed resource is the MapServer. Its underlying record has no license title, and the service states BIG copyright without reuse terms. Public query access does not by itself establish permission to copy the full geometry into this service's own public vector tiles. Confirm permitted copying, transformation, attribution, and tile redistribution with BIG before publication. Until then, the official service can support a limited technical proof, but the planned self-hosted tiles are not cleared. [Dataset entry](https://data.go.id/dataset/dataset/batas_kecamatan_ar_2026) · [service metadata](https://geoservices.big.go.id/rbi/rest/services/BATASWILAYAH/BATAS_KECAMATAN_AR/MapServer?f=pjson)

## Coverage and geometry check

On 27 September 2026, I queried BIG's live layer for province codes `31`–`36` (Jakarta, West Java, Central Java, Yogyakarta, East Java, and Banten). It returned **2,157 polygon features**: **2,146 unique, nonblank `KDCPUM` codes** and **11 unallocated polygons with no usable *kecamatan* code** (10 in East Java, one in West Java). Every nonblank code matched the `NN.NN.NN` format and its province and district prefix. No `KDCBPS` value was populated in these 2,146 rows, so use `KDCPUM`, not the BPS code or the service `OBJECTID`, for the join. These are live-service counts; freeze and recheck them when taking the import snapshot. The six-province query includes islands administered by those provinces, including Kepulauan Seribu. A strict Java-island map needs a separate geographic mask. [BIG layer schema](https://geoservices.big.go.id/rbi/rest/services/BATASWILAYAH/BATAS_KECAMATAN_AR/MapServer/0?f=pjson) · [six-province count query](https://geoservices.big.go.id/rbi/rest/services/BATASWILAYAH/BATAS_KECAMATAN_AR/MapServer/0/query?where=KDPPUM%20IN%20%28%2731%27%2C%2732%27%2C%2733%27%2C%2734%27%2C%2735%27%2C%2736%27%29&returnCountOnly=true&f=json)

I fetched 60 polygons, ten from each province, as GeoJSON and checked them with Shapely 2.0.3. All 60 parsed as valid Polygon or MultiPolygon geometry. This sample does **not** prove that all Java geometry is valid, that adjacent polygons share edges, or that there are no gaps or overlaps. The full import must run geometry and topology checks. [BIG GeoJSON query endpoint](https://geoservices.big.go.id/rbi/rest/services/BATASWILAYAH/BATAS_KECAMATAN_AR/MapServer/0/query) · [BIG dataset description](https://data.go.id/dataset/dataset/batas_kecamatan_ar_2026)

BIG's own description gives stronger reasons for caution: the underlying village data mixes definitive, agreed, and indicative boundaries. It reports unallocated islands and lakes, missing geometry for some villages, possible competing claims in indicative areas, and places where village and district boundaries do not align. It names DKI Jakarta among the misaligned areas. Thus these polygons are suitable as **dated administrative screening areas**, subject to import checks; they are not a checked farming-zone boundary, legal parcel boundary, or proof that every point belongs to one *kecamatan*. [BIG dataset description](https://data.go.id/dataset/dataset/batas_kecamatan_ar_2026)

## ID and version rule

Store the published boundary release ID and the `KDCPUM` **string** together as the area key. Keep the raw code with periods and the official name and parent codes from that release. Tiles and summary rows must use the same snapshot. Do not key durable records by `OBJECTID`: BIG labels that field only as the service's object ID, and the layer states `isDataVersioned: false`. The portal says the June 2026 layer used the 2025 Kemendagri code decision for island allocation. [BIG dataset description](https://data.go.id/dataset/dataset/batas_kecamatan_ar_2026) · [BIG layer schema](https://geoservices.big.go.id/rbi/rest/services/BATASWILAYAH/BATAS_KECAMATAN_AR/MapServer/0?f=pjson) · [Kemendagri 2025 decision record](https://peraturan.bpk.go.id/Details/322912/keputusan-mendagri-no-30022-2430-tahun-2025)

`KDCPUM` is an official administrative identifier, but **not a promise of fixed geometry or a timeless area**. Permendagri 58/2021 says a split keeps the parent *kecamatan* code and assigns a new code to the new *kecamatan*; a name change keeps the code. Merger rules can retain one old code or issue a new one, depending on the chosen name. The regulation allows annual updates, or additional updates when needed. BIG also says coastlines and boundaries can change between map editions and asks thematic map makers to show the edition used. [Permendagri 58/2021, arts. 7 and 13](https://ditjenbinaadwil.kemendagri.go.id/download/file/PMDN_Nomor_58_tahun_20211.pdf) · [BIG July 2026 release](https://big.go.id/content/siaran-pers/rilis-mengapa-luas-wilayah-di-peta-bisa-berubah)

For a later release, stage its code list and polygons beside the old snapshot. Compare added, removed, and retained codes, names, parents, and geometry. Record a reviewed change table with old and new release IDs, codes, and relation (`unchanged`, `geometry changed`, `split`, `merged`, `renamed`, or `unresolved`), with spatial overlap as supporting evidence. Recompute NASA summaries for the new geometry; do not carry area statistics across a changed boundary as if the area stayed fixed. Keep old summaries available with their old release. This is the project's proposed handling, based on the regulation and BIG's edition guidance. [Permendagri 58/2021](https://ditjenbinaadwil.kemendagri.go.id/download/file/PMDN_Nomor_58_tahun_20211.pdf) · [BIG edition guidance](https://big.go.id/content/siaran-pers/rilis-mengapa-luas-wilayah-di-peta-bisa-berubah)

## Later checked farming zone

Give each locally checked farming zone its **own stable zone ID** and dated, checked geometry. Link that zone to the boundary release and `KDCPUM` used at the time of review, with the overlap method and reviewer recorded. If a zone crosses *kecamatan* borders, keep a many-to-many link with overlap shares or mark its primary area by an explicit local rule; do not silently force one code. On a boundary update, re-run the spatial link and have a local reviewer resolve changed or ambiguous assignments. The zone ID can then remain the link across map, crop history, and rotation comparison while *kecamatan* context changes by release. This is a design inference from the project's [farming-zone decision](../../.scratch/field-shift-java/issues/09-define-zone-and-map-claims.md) and BIG's documented boundary gaps. [BIG dataset description](https://data.go.id/dataset/dataset/batas_kecamatan_ar_2026)
